# API 호환성 사용 현황 확인

`UMC Product` 폴더의 **API 호환성 · 사용 현황**은 구 API 제거를 검토할 때 호출 근거를 찾는
화면이다. Grafana UID는 `umc-product-api-lifecycle`이다. 현재 배포·수집 상태와 실제 보유
데이터는 화면에서 확인해야 하며, 저장소 설정만으로 정상 수집 중이라고 판단하지 않는다.

## 후보 API 확인 순서

1. `Service`를 선택한다. 기본값은 `prod-umc-product`이며 dev/local과 preview의 정확한
   서비스 이름도 사용할 수 있다. 선택지의 존재는 해당 앱이 실행 중이라는 뜻이 아니다.
2. 기본 1시간으로 수집 상태를 확인하고, 필요하면 6시간·1/7/14/30일로 늘린다.
   모든 Loki 패널은 현재부터 선택한 기간을 조사한다. 긴 기간은 먼저 메서드·경로 조건을
   좁힌 뒤 조회한다. 자동 새로고침은 꺼져 있으므로 다시 조사할 때 화면을 새로고침한다.
3. HTTP 메서드와 경로 템플릿으로 후보 API를 좁힌다. 경로는 실제 ID가 들어간 URL 대신
   `/api/v1/challengers/{challengerId}` 같은 서버 템플릿을 입력한다. 경로 필터는 정규식이 아닌
   문자열 포함검색이므로 비슷한 경로가 함께 잡히면 `API별 관측 호출 수`에서 구분한다.
4. 클라이언트·버전별 호출과 버전 계측 상태를 확인한다. 요청 건수는 사용자 수나 설치 수가 아니다.
5. `최근 관측 요청` 첫 행의 시각을 기록한다. 최신 200건이며 선택 기간 안의 마지막 관측이지
   서비스 전체 수명에서 마지막으로 호출한 시각을 보장하지 않는다.
6. 아래 제거 이슈에 서비스, 메서드·템플릿, 조사 시각·기간, Grafana 링크, 계측 누락과 수집
   이상 여부를 남긴다. 지원 클라이언트의 전환 릴리스와 검토 책임자를 함께 기록한다.

- [제거 검토 이슈 만들기](https://github.com/UMC-PRODUCT/umc-product-server/issues/new?template=api-lifecycle.yml)
- [서버의 API 호환성 관리 절차](https://github.com/UMC-PRODUCT/umc-product-server/blob/develop/docs/onboarding/api-lifecycle.md)

## 버전 상태 해석

서버는 선택 헤더 `X-Client-Version`을 읽어 완료 로그에 `clientVersion`,
`clientVersionStatus`를 기록한다. 앱·웹의 공통 HTTP 클라이언트가 매 요청에 버전을 보내야 한다.
서버 계측 배포만으로 기존 앱의 버전을 알 수는 없다. 헤더가 없거나 잘못되어도 요청은 허용한다.

| 상태 | 의미 | 화면의 버전 |
|---|---|---|
| `provided` | 유효한 버전 헤더를 보낸 요청 | 전달한 버전 |
| `missing` | 헤더가 없는 요청 | `UNKNOWN` |
| `invalid` | 빈 값·중복·허용 형식 밖의 헤더 | `UNKNOWN` |
| `not_instrumented` | 상태 속성 자체가 없는 로그 | 버전 속성도 없으면 `NOT_INSTRUMENTED` |

`not_instrumented`는 구서버 계측 또는 속성 수집을 확인해야 한다는 뜻이다. 대시보드가 조회할 때
붙이는 표시이며 서버가 보낸 상태가 아니다. `UNKNOWN`을 새 버전이나 구 버전으로 추정하지 않는다.
클라이언트 종류는 `clientService`를 사용한다. 기기 종류만으로는 iOS 앱과 iOS 웹을 구분할 수 없다.

## 관측 기간과 No data

- 패널의 오류 아이콘은 조회 실패다. 아이콘의 메시지부터 확인한다. 특히 `connection refused`는
  0건 응답이 아니라 Loki 연결 실패이며, Loki readiness·재시작 횟수·`OOMKilled` 여부를 확인한다.
  오류가 난 상태에서 장기간 새로고침을 반복하지 않는다. `No data` 표시와 구분해서 기록한다.
- 단일 Loki의 메모리 한도는 768Mi이며 쿼리 동시 실행과 분할 병렬도를 각각 최대 2로 제한한다.
  `GOMEMLIMIT=512MiB`는 Go 런타임의 소프트 메모리 한도이며 OOM을 완전히 방지하는 보장은 아니다.
  장기간 집계는 대기·조회 시간이 늘 수 있다. 시간 초과가 나면 기간을 나눠 조사하고,
  빈 결과로 간주하지 않는다. 반복적인 월간 전체 집계는 사전 집계나 별도 용량 검토가 필요하다.
- Loki 보관 선언은 90일이다. 이 화면의 선택지는 조회 비용을 줄이기 위해 최대 30일이며,
  실제 보유 데이터·Loki 쿼리 제한·오류 여부를 별도로 확인해야 한다. 90일 전체를 한 번의
  쿼리로 조회할 수 있다고 가정하지 않는다. 과거 기간 조사는 담당자와 Explore에서 범위를 나눠 진행한다.
- Prometheus 보관 선언은 14일/4GB다. 이 화면의 전체 HTTP 요청량과 Collector 전송 실패는
  최근 5분의 참고값이며 선택한 후보 API·클라이언트 필터와 무관하다. 과거 전체 기간의 로그
  수집 정상 여부를 증명하지 않는다.
- `No data`, 빈 목록, 쿼리 오류는 0건으로 처리하지 않는다. 데이터소스 오류, 계측 도입 전 기간,
  보관 만료, Collector 수신 거부·전송 실패, Loki 폐기 지표와 실제 로그를 확인한다.
- 완료 로그는 MVC 인터셉터가 기록한 요청만 포함한다. 인증 필터에서 끝난 요청, 미완료 요청,
  유실 로그 등은 HTTP 메트릭과 수집 범위가 다를 수 있다.
- 호출이 한 번도 관측되지 않은 API는 목록에 나타나지 않는다. 전체 API 목록·OpenAPI·서버 라우팅과
  대조하고, 미관측 대상을 제거 이슈에서 별도로 검토한다.
- 모집·기수별 기능은 30일 안에 호출되지 않을 수 있다. 실제 업무 주기, 구버전 지원 정책,
  휴면 사용자의 재접속까지 고려하고 사용량만으로 삭제하지 않는다.
- 응답 필드 소비는 HTTP 로그로 알 수 없다. iOS·Android·웹의 출시 코드와 전환 릴리스를 확인한다.
  GraphQL의 `/graphql` 호출량 또한 개별 GraphQL 필드 사용량이 아니다.

## 수집 계약과 개인정보

앱 → OTLP Collector → Loki의 기존 경로를 사용한다. 앱 MDC 속성은 Loki structured metadata로
조회하며 JSON 본문을 가정하는 `| json`을 사용하지 않는다. 원문 앱 버전은 Loki 인덱스 label이나
Prometheus label에 넣지 않는다. 이 화면을 위해 새 수집기나 알림 전송 경로를 만들지 않는다.

최근 요청 패널은 허용한 메서드·경로 템플릿·클라이언트·버전·상태만 남기고 본문을 다시 구성한다.
사용자 ID, IP, 실제 요청 URL, trace ID는 조회 결과에서 제외한다. 기존 전체 로그의 저장·접근 정책을
바꾸는 기능은 아니므로 Explore나 다른 로그 화면에서 공유할 때는 기존 개인정보 확인 절차를 따른다.

## 배포 후 확인

서버 계측과 클라이언트 헤더 변경이 배포된 뒤 담당자가 dev에서 정상 버전 요청, 헤더 없는 요청,
잘못된 헤더 요청을 각각 보내고 `provided/missing/invalid`와 최근 로그 시각을 확인한다.
기존 계측 전 로그가 있으면 `not_instrumented`로 구분되는지 확인한다. 없는 후보 경로를 입력했을 때
0건·제거 가능 판정이 아닌 관측 데이터 없음으로 나타나야 한다.

로컬 합성 로그 검증은 쿼리 동작만 확인한다. 실제 운영 Grafana 화면과 필드 이름, 전체 기간의
수집 연속성, 클라이언트 릴리스 전환 확인을 대체하지 않는다.
